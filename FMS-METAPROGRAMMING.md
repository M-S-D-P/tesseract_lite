# Proving the static-analysis gap on FMS

A walkthrough for the objection raised in review: *static code analysis cannot
reliably determine dynamically generated methods, so how do you know?*

The answer is that we do not infer it. We watch the application run and check
what actually executed against the source we indexed. This document names the
exact FMS pages to click, the exact files and line numbers involved, and what
the evidence looks like — so the claim can be checked rather than believed.

Everything below was read out of `fms-main` (Rails 6.1, 978 models, 360
controllers) and out of Ruby 3.3's own behaviour, measured rather than assumed.

---

## 1. Why the source genuinely cannot tell you

FMS generates methods four different ways. Counted across `app` and `lib`:

| Mechanism | Files | What it produces |
|---|---|---|
| `store_accessor_*` macros (`lib/store_accessor_type_safety.rb`) | 123 | typed hstore attribute readers/writers |
| `ActiveSupport::Concern` | 139 | methods mixed in from elsewhere |
| `delegate` | 131 | forwarding methods |
| `define_method` | 52 | methods whose names are built from strings |
| `method_missing` | 11 | methods that never exist at all |

Take `app/models/tenant.rb`. It is 1,488 lines and includes 19 concerns. Lines
307–326 read:

```ruby
store_accessor_boolean :military_information, :military_attestation
store_accessor_date    :military_information, :date_entered_service
store_accessor_string  :military_information, :military_rank
…
```

There is no `def military_rank` anywhere in FMS. Grep for it and you find the
macro call, not a method. The method is manufactured at class-definition time by
`lib/store_accessor_type_safety.rb`. A reviewer reading `tenant.rb` sees a
declaration; the running app has a method.

That is the gap. Now the important part: **how Ruby reports such a method
decides what we can prove**, so we measured it instead of guessing.

---

## 2. What Ruby actually reports (measured)

Ruby records a `define_method` body's location at **the block's own position**,
and a backtrace frame is labelled `block in <enclosing scope>`. Probing Ruby
3.3.5 with the FMS patterns gives:

| How the method was made | `source_location` points to | Backtrace frame label |
|---|---|---|
| `define_method` written **in the model file** | that model file | `block in <class:Tenant>` |
| `define_method` inside a **macro or concern** | the macro/concern file | `block in store_accessor_string` |
| `delegate` (Rails passes the caller's file/line) | the model file | the delegated method's own name |
| Rails' own attribute/association methods | inside the activerecord gem | filtered out by Rails' backtrace cleaner |

Every SQL statement Rails logs carries the attribution line beneath it:

```
  Ledger Load (0.9ms)  SELECT "ledgers".* FROM …
  ↳ app/models/facility.rb:1795:in `block in <class:Facility>'
```

So the honest split is:

- **Generated in the model file** → the frame is `block in <class:X>`, which is
  not a `def` in that file. We flag it. **True positive, on real Rails output.**
- **Generated by a macro or concern** → the frame names the *macro*
  (`block in store_accessor_string`), and that macro *is* defined in the file
  the line points at. We report it as defined, because it is. What we prove here
  is that the generator ran, not the name of each method it made.
- **Rails' own generated methods** → they never get their own frame, because the
  backtrace cleaner drops gem code. They are invisible to a method-level check
  and are instead caught at the table/SQL level and by the controller-level
  static-versus-runtime gap.

This is a narrower claim than "we find all metaprogramming", and it is the one
that survives scrutiny.

## Example 1 — Facility fees: a generated method that runs a dynamic finder

**The strongest one.** Both halves of the objection in a single line of code.

`app/models/facility.rb:1788–1797`:

```ruby
[:admin_fee, :invoice_fee, :security_deposit, :fee_nsf,
 :california_fee_schedule].each do |fee_name|
  define_method fee_name do
    invoiceable_items.find_by_product_code(FeeInvoiceableItem::Types.const_get(fee_name.upcase))
  end
end
```

Three things are true at once:

1. `Facility#admin_fee` is **not written anywhere**. It is built from a symbol
   in a loop.
2. Its body calls `find_by_product_code` — an ActiveRecord **dynamic finder**,
   resolved through `DynamicMatchers`, which is precisely the
   `find_by_user_id`-class method raised in review.
3. It **issues SQL**, so Rails logs it with an attribution line.

**Page to visit:** any facility settings or fee page — e.g. *Facility →
Settings → Fees*, or move-in pricing, anything that renders fee amounts. Paths
look like `/company/:company_id/facility/:facility_id/…`.

**Expected evidence:** a finding whose file is `app/models/facility.rb` and
whose frame is `block in <class:Facility>`, because no such `def` exists in that
file. The query beside it is the `invoiceable_items` lookup.

**Why static analysis loses:** to know `admin_fee` exists you must evaluate the
array literal, the loop, and `const_get(fee_name.upcase)`. To know what it
*queries* you must resolve a finder that ActiveRecord itself synthesises.

## Example 3 — Update customer: three generation mechanisms in one Save

This is the "update customer" flow you asked for. One click traverses three
different ways of manufacturing a method, and not one of the methods involved is
written as a `def`.

**Page:** *Tenant → Edit → Save*
`PATCH /company/:company_id/facility/:facility_id/tenants/:id`
→ `TenantsController#update` (`app/controllers/tenants_controller.rb:161`)

The action calls `set_insurance_exclusion_information` (line 188), which reads
and writes the insurance-exclusion fields:

```ruby
old_excluded = @tenant.exclude_from_insurance_auto_enroll            # ← layer 1
…
@tenant.settings.exclude_from_insurance_auto_enroll_created_by = current_user.id   # ← layer 2
```

Follow each name through the source:

**Layer 1 — `delegate`.** `app/models/tenant.rb:487–494`:

```ruby
delegate :exclude_from_insurance_auto_enroll,
         :exclude_from_insurance_auto_enroll_created_by,
         :exclude_from_insurance_auto_enroll_on, to: :settings
```

`Tenant#exclude_from_insurance_auto_enroll` is a forwarding method Rails writes
for you. Rails passes the *caller's* file and line to `module_eval`, so the
attribution line will read `app/models/tenant.rb:487:in
'exclude_from_insurance_auto_enroll'` — a method name that appears in that file
only as an argument to `delegate`.

**Layer 2 — `store_accessor`.** The target is `TenantSettings`
(`tenant.rb:101`, `has_one :settings, class_name: 'TenantSettings'`), and
`app/models/tenant_settings.rb:51–54`:

```ruby
store_accessor_boolean :data, :exclude_from_insurance_auto_enroll, false
store_accessor_string  :data, :exclude_from_insurance_auto_enroll_reason
store_accessor_integer :data, :exclude_from_insurance_auto_enroll_created_by
store_accessor_date    :data, :exclude_from_insurance_auto_enroll_on
```

These are readers and writers over a JSONB `data` column, generated by
`lib/store_accessor_type_safety.rb`. `store_accessor_integer`'s writer coerces
the value; `store_accessor_date` also registers a format validation that runs on
save. Again: no `def`.

**Layer 3 — `method_missing`, as the fallback.** `TenantSettings < Setting`, and
`app/models/setting.rb:97` answers any key present in `DEFAULTS` that has no
store accessor at all — checking the key, coercing by the default's declared
type, and marking the JSONB column dirty:

```ruby
def method_missing method_name, *args, &block
  key = called_method.chomp '='
  return super if attributes.keys.include?(key)
  return super unless self.class::DEFAULTS.has_key? key
  …
```

`TenantSettings::DEFAULTS` (line 8) is a hash of ~40 keys. For those, the method
does not exist even after boot — it is answered per call. And line 2 adds a
fourth flavour for good measure: `alias_method :tenant, :owner`.

**Why static analysis loses:** to enumerate what a `TenantSettings` responds to
you must evaluate a `delegate` list, a set of macro calls, *and* a hash consulted
at call time. `respond_to?` is decided dynamically. Reading `tenant.rb` shows
declarations; the running object has methods.

**Expected evidence:** the request with its `UPDATE … SET data = …` JSONB write,
attributed into `app/models/tenant.rb` (the delegate line) and
`lib/store_accessor_type_safety.rb`. Per section 2 the macro file is reported as
**defined** — the macro genuinely is there — so the honest statement is: *these
method names exist nowhere as definitions, here is the request that invoked
them, here is the SQL it caused, and here are the four mechanisms that produced
them.* Ask **What metaprogramming ran?** on that request and the model must
ground its answer in the report rather than in what Rails usually does.

## Example 4 — Update military information: 26 generated writers in one POST

**Page:** *Tenant → Military* → Save
`PATCH /company/:company_id/facility/:facility_id/tenants/:id/military`
→ `TenantsController#update_military` (line 80), routes line 958.

The action is four lines:

```ruby
@tenant.assign_attributes(military_params)
@tenant.save
```

`military_params` (line 267) permits 26 attributes — `military_attestation`,
`date_entered_service`, `military_rank`, `place_of_birth`, `last_4_of_ssn`,
`branch_of_service`, … — and **every one is a generated hstore accessor** from
`tenant.rb:312–326`. `assign_attributes` calls 26 writers that do not exist as
`def`, each created by `define_method("#{key}=")` in
`lib/store_accessor_type_safety.rb`, several of which coerce and validate on the
way through (`store_accessor_date` parses strings into dates and registers a
format validation).

**Expected evidence:** the request, its `UPDATE tenants SET military_information
= …` hstore write, and attribution into
`lib/store_accessor_type_safety.rb`. Per section 2 this is reported as
**defined** — the macro is genuinely there — so the honest statement is: *the
generator ran, here is the request that made it run, and here are the 26 names
it produced,* the last of which comes from reading the macro **calls** in
`tenant.rb`, not from guessing.

## Example 5 — Controllers that exist only at runtime

Not a method but the same principle, and it needs no log-line subtlety.

**What to do:** exercise any engine-mounted or dynamically routed area of FMS
(`engines/` in the repo), then open **Code coverage from live traffic** on
`/live`.

**Expected evidence:** three numbers no APM can produce, because an APM never
parsed the source — controllers in the source that serve traffic, controllers in
the source that serve none (deprecation candidates), and **controllers serving
traffic that static analysis never found at all**. That last list is the
metaprogramming blind spot made visible.

Measured on an indexed Discourse corpus for comparison: 136 controllers in
source, 10 exercised by traffic, 126 unexercised.

## What to say when challenged

**"Prove it, don't tell me."**

```bash
node scripts/verify-metaprogramming.mjs \
  --base http://localhost:3005 --email you@example.com --password '...'
```

It indexes a fixture whose answer is known in advance, streams a matching log,
and fails unless the generated method is found, methods genuinely present in the
source are *not* misreported, and a file that is not indexed is refused rather
than called metaprogramming. Exits non-zero, so it can run in CI.

**"Could it just be guessing?"** Every verdict names the file, the method, the
execution count and how much indexed source backed the judgement. A file that is
not in the corpus is reported as unjudged, never as evidence.

**"What does it miss?"** Stated plainly: a generated method that never touches
the database emits no attribution line and is invisible here; methods generated
inside a macro are attributed to the macro, so we prove the generator ran rather
than naming each product; and Rails' own attribute and association methods are
removed from backtraces by Rails itself, so they are caught at the SQL and
controller level instead. This finds dynamically generated code **on the paths
your traffic actually exercised** — which is a claim about evidence, not about
completeness.
